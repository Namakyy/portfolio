Project Summary EN

Traffic Simulation is a Python desktop application built for the SAÉ S3.02 module at IUT Réseaux & Télécommunications. It simulates a signalised intersection: vehicles appear randomly, obey traffic lights, keep a safe distance, turn left or right when the target lane is free, and can park in a car park with a live count of free spaces. Emergency vehicles can be created from a control panel: the lights turn green for them and the other cars pull over.

The interface is built with PyQt6 and the simulation runs with threads. The next steps are a TCP socket client/server architecture, a database for history and statistics, and a deployment that works on Linux, macOS and Windows.

1. Contexte de la compétence & situation professionnelle

Cadre. La SAÉ S3.02 « Développer des applications communicantes » demande de concevoir en Python une application dont les composants échangent par le réseau, en utilisant des threads, des sockets et une base de données. Les consignes détaillées étant limitées, l'équipe a défini elle-même son cahier des charges (voir les preuves), avec une contrainte que nous nous sommes fixée : une application qui fonctionne sous Linux, macOS et Windows.

Situation professionnelle. Le sujet traité est la simulation d'un carrefour à feux avec trafic aléatoire, parking et véhicules prioritaires. Il équivaut à un outil de supervision utilisé en interne par une équipe de gestion du trafic : un opérateur visualise la circulation et déclenche des interventions d'urgence. Cela correspond à la situation professionnelle du référentiel pour cette compétence : « Développement d'outils informatiques à usage interne d'une équipe ».

Phases du projet. (1) modélisation de l'architecture logicielle en classes ; (2) développement de la simulation et de l'interface graphique ; (3) fiabilisation : blocages, collisions, priorités ; (4) extensions : parking et véhicules prioritaires ; (5) passage à une application communicante : threads, puis sockets, base de données et déploiement.

3. Description réflexive de l'activité

Ce que j'ai fait précisément.
J'ai modélisé le carrefour en classes séparées en trois couches (modèle, logique de simulation, interface), écrit les règles de circulation (feux, arrêts, distance de sécurité, virages), réalisé l'affichage PyQt6, ajouté le parking, puis intégré les véhicules prioritaires à la branche principale. Les threads sont en place ; les sockets, la base de données et le déploiement sont les prochaines étapes.

Ma démarche.
J'avance par petites étapes : j'ajoute une règle, je la teste visuellement dans la simulation, puis je corrige. Quand le comportement est incompréhensible, j'affiche des informations de diagnostic (état, position, cause d'un arrêt) pour savoir quelle condition se déclenche, avant de modifier le code.

Difficultés rencontrées et solutions.
  • Interface figée par time.sleep(). Ma première version du cycle des feux faisait des pauses bloquantes : toute la fenêtre se figeait, car Qt n'utilise qu'un seul fil pour l'interface. J'ai compris le rôle de la boucle d'événements et remplacé les pauses par un compteur décrémenté à chaque tick du QTimer, dans une machine à états.
  • Erreurs d'encapsulation. Accès à des attributs privés depuis l'interface, appel d'une méthode sans parenthèses (get_x au lieu de get_x()), méthode écrasée par un entier ('int' object is not callable). Corrigé avec des accesseurs et mutateurs, en lisant les messages d'erreur ligne par ligne.
  • Boucle imbriquée. Une boucle sur les quatre directions contenant la boucle sur tous les véhicules les faisait avancer quatre fois par tick. Le point d'apparition dérivait aussi hors de l'écran et les nouveaux véhicules étaient supprimés aussitôt. Trouvé en relisant la structure des boucles.
  • Interblocages au carrefour. Des véhicules se bloquaient mutuellement pour toujours. J'ai affiché « qui bloque qui » pour comprendre la chaîne. J'ai essayé un mécanisme de « patience » qui forçait le passage après un délai, puis je l'ai retiré : il provoquait des collisions au feu rouge. Leçon : on ne résout pas un conflit de priorité en assouplissant la règle de sécurité.
  • Détection de collision. Comparer la distance à toutes les voitures arrêtait des véhicules situés sur d'autres voies. J'ai limité la détection aux véhicules devant, sur la même voie, avant de calculer la distance.
  • Intégration de deux branches. La branche des véhicules prioritaires et la branche principale (avec le parking) modifiaient les mêmes fichiers. Fusion manuelle en gardant les deux fonctionnalités. Leçon : découper les responsabilités et passer par des pull requests évite ces conflits.
  • Sorties de parking. Certaines voitures s'arrêtaient sans raison apparente. Mon hypothèse : il manquait une vraie attente avant de s'engager sur la route et une vérification plus lointaine de l'arrivée d'une voiture. J'ai ajouté une attente et un seuil de distance, puis retesté.
Ce que j'ai appris.
Séparer le modèle, la logique et l'affichage ; utiliser une machine à états pour tout ce qui dépend du temps ; tester une modification à la fois ; traiter un blocage en comprenant sa cause plutôt qu'en le contournant ; fusionner deux versions d'un même code.

Ce que je veux approfondir.
La protection de l'état partagé entre plusieurs threads (verrous), la conception d'un protocole de messages entre client et serveur, l'accès concurrent à une base de données, des tests automatisés de la simulation sans interface et le packaging multiplateforme.

Transparence.
J'ai utilisé un assistant d'IA pour comprendre des erreurs, comparer des approches et relire du code. Chaque proposition a été lue, testée dans la simulation, puis adaptée ou rejetée : c'est le cas du mécanisme de « patience », que j'ai retiré après avoir constaté ses effets.

for autre in self.__vehicules:
    if autre is vehicule:
        continue

    dx = autre.get_x() - vehicule.get_x()
    dy = autre.get_y() - vehicule.get_y()

    devant = False
    if vehicule.get_direction() == "droite" and dx > 0 and abs(dy) < 20:
        devant = True
    elif vehicule.get_direction() == "gauche" and dx < 0 and abs(dy) < 20:
        devant = True
    elif vehicule.get_direction() == "bas" and dy > 0 and abs(dx) < 20:
        devant = True
    elif vehicule.get_direction() == "haut" and dy < 0 and abs(dx) < 20:
        devant = True

        distance = (dx ** 2 + dy ** 2) ** 0.5

src/simulation/simulation.py - voie_libre() : un véhicule ne tourne que si la voie d'arrivée est libre
def voie_libre(self, vehicule):
    seuil = 60

    for autre in self.__vehicules:
        if autre is vehicule:
            continue

        # HAUT -> BAS
        if vehicule.get_direction() == "bas":
            if autre.get_direction() == "haut":
                if abs(autre.get_y() - vehicule.get_y()) < seuil:
                    if autre.get_destination() in (None, "gauche"):
                        continue

                    if autre.get_destination() == "droite":
                        return False
        # ... mêmes tests pour les trois autres directions
    return True
